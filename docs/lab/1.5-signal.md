# 1.5 信号 Signal —— 让节点之间不再互相伸手

> 单元编号：1.5 ｜ 预计 45 分钟 ｜ 前置：1.1 节点与场景树、1.2 生命周期

---

## 一、它解决什么问题

先看你写过的东西。在 `first2dgame` 里，玩家受伤后 HUD 要更新血量，最常见的写法是：

```gdscript
# player.gd —— 反面教材
func take_damage(amount: int) -> void:
    health -= amount
    get_node("../HUD/HealthBar").value = health
```

这一行能跑，但它埋了四个雷：

1. **玩家脚本必须知道 HUD 的完整路径**。你哪天把 HUD 挪进 `CanvasLayer`，这一行就崩。
2. **玩家必须知道 HUD 的接口**。HUD 从 `ProgressBar` 换成自绘的 `TextureProgressBar`，玩家也得改。
3. **玩家被复用到没有 HUD 的场景**（比如做一个纯战斗测试场景），直接空指针。
4. **无法单独测试玩家**。想测「受伤后血量扣得对不对」，必须先搭一个 HUD。

信号把这一行拆成两半：

- 玩家只广播一句「我血量变了，现在是 70/100」，**不关心谁在听**；
- HUD 自己决定「我关心这件事」，并订阅。

这叫**观察者模式**。Godot 把它做成了语言级特性，不需要你手写一套事件管理器。

**一句话本质：信号是节点发出的广播，连接是订阅。发送方与接收方互不引用。**

## 二、它的形状：先看接口

信号相关的 API 很少，一次记完。

### 自定义信号

| 写法 | 作用 |
|---|---|
| `signal health_changed(current: int, maximum: int)` | 声明信号，可带参数与类型标注，一般写在脚本顶部 |
| `health_changed.emit(70, 100)` | 发出信号，参数必须匹配声明 |
| `health_changed.connect(_on_health_changed)` | 订阅，参数是 `Callable` |
| `health_changed.disconnect(_on_health_changed)` | 取消订阅 |
| `health_changed.is_connected(_on_health_changed)` | 查询是否已连接 |
| `health_changed.get_connections()` | 拿到当前所有订阅者，调试很好用 |

### 连接时的附加参数

`connect` 还能传一个 flag：

| flag | 作用 |
|---|---|
| `CONNECT_ONE_SHOT` | 只触发一次，触发后自动断开 |
| `CONNECT_DEFERRED` | 延迟到空闲帧再执行回调，用于「信号里不要立刻改场景树」的场合 |
| `CONNECT_PERSIST` | 编辑器里连的信号用这个，代码里一般不用 |

以及给回调预填参数：

```gdscript
some_signal.connect(_on_hit.bind("head"))   # _on_hit(damage: int, part: String)
```

### 内置信号——你已经用过但可能没当回事

几乎每个节点都自带信号，这些**不需要你自己声明**：

| 节点 | 常用内置信号 |
|---|---|
| `Button` / `BaseButton` | `pressed`、`button_down`、`toggled(bool)` |
| `Timer` | `timeout` |
| `Area2D` | `body_entered(body)`、`area_entered(area)`、`body_exited` |
| `AnimationPlayer` | `animation_finished(name)`、`animation_started` |
| `AnimationTree` | `animation_finished` |
| `AudioStreamPlayer` | `finished` |
| `Node` | `ready`、`tree_entered`、`tree_exiting`、`renamed` |

**判断标准**：内置信号 = 引擎在某个确定时刻帮你 `emit()`。你只要 `connect`，不用管它什么时候发。

## 三、最小可运行例子

**目标**：玩家受伤 → HUD 血条自动更新 → 血量归零 → 播放死亡动画。全程玩家不认识 HUD。

### 场景结构

```
Main (Node2D)
├── Player (CharacterBody2D)        ← 加入组 "player"
│   ├── CollisionShape2D
│   └── Sprite2D
└── HUD (CanvasLayer)
    └── Panel (Control)
        ├── HealthBar (ProgressBar)   ← max_value = 100
        └── HealthLabel (Label)
```

### player.gd

```gdscript
extends CharacterBody2D

signal health_changed(current: int, maximum: int)
signal died

@export var max_health: int = 100
var health: int = max_health

func _ready() -> void:
    add_to_group("player")
    health_changed.emit(health, max_health)   # 开局先广播一次，HUD 不用自己初始化

func take_damage(amount: int) -> void:
    if health <= 0:
        return
    health = maxi(health - amount, 0)
    health_changed.emit(health, max_health)
    if health == 0:
        died.emit()

func heal(amount: int) -> void:
    health = mini(health + amount, max_health)
    health_changed.emit(health, max_health)
```

### hud.gd

```gdscript
extends CanvasLayer

@onready var bar: ProgressBar = $Panel/HealthBar
@onready var label: Label = $Panel/HealthLabel

func _ready() -> void:
    var player := get_tree().get_first_node_in_group("player")
    if player == null:
        push_error("HUD 找不到组为 player 的节点")
        return
    player.health_changed.connect(_on_health_changed)
    player.died.connect(_on_player_died)

func _on_health_changed(current: int, maximum: int) -> void:
    bar.max_value = maximum
    bar.value = current
    label.text = "%d / %d" % [current, maximum]

func _on_player_died() -> void:
    label.text = "你死了"
    # 这里可以接死亡动画、暂停、弹结算面板
```

### 验证

在 `Main` 上挂一个临时脚本，按空格扣血：

```gdscript
extends Node2D

func _unhandled_input(event: InputEvent) -> void:
    if event.is_action_pressed("ui_accept"):
        $Player.take_damage(15)
```

跑起来，按空格十次，血条从满到空，最后显示「你死了」。**注意：`player.gd` 里没有出现过一次 `HUD` 这个词。**

## 四、逐行拆解：这些行为什么这么写

**1. `signal health_changed(current: int, maximum: int)` 写在脚本顶部，不是类里面**

GDScript 的 `signal` 是类成员声明，必须放在函数外。带类型标注是有意义的：`connect` 的回调签名对不上时，Godot 会在连接时报错，而不是运行时静默失败。

**2. `_ready` 里先 `emit` 一次**

这是新手最常漏的一步。HUD 的 `_ready` 和 Player 的 `_ready` 谁先执行，取决于它们在场景树里的顺序。如果你只在受伤时广播，HUD 初始显示的就是场景里摆的默认值，一旦和真实血量不一致就出 bug。**开局广播一次，让接收方永远从信号里拿状态。**

**3. `health = maxi(health - amount, 0)` 而不是 `health -= amount`**

`maxi` 保证血量不为负。区别在 `died` 的判定：用 `if health <= 0` 时，血量可能变成 -20，HUD 血条会显示成负数进度，进度条渲染异常。

**4. `get_first_node_in_group("player")` 而不是 `get_node("../Player")`**

组是**按语义找节点**，路径是**按位置找节点**。前者在场景重构后依然有效。这是 1.11 组 Group 的预演，你现在就可以先用起来。

**5. `if player == null: push_error(...)` 这个判断不能省**

`get_first_node_in_group` 找不到时返回 `null`，接着 `.connect` 会抛 `Attempt to call function 'connect' on a null instance`。这个报错信息完全不提「你忘了加组」，加上自己的一句错误提示，能省半小时排查。

**6. `_on_health_changed` 命名带 `_on_` 前缀**

不是强制，是约定。编辑器里连信号会自动生成这个名字，所有人（包括未来的你）一看就知道这是信号回调，不是业务逻辑。

## 五、变式实验：改一处，看一个现象

按顺序做，每个大约 5 分钟。

**实验 A：把同一件事连两次**

在 `hud.gd` 的 `_ready` 末尾再加一行 `player.health_changed.connect(_on_health_changed)`。运行，按一次空格。

现象：血量标签显示两次更新（如果加个 `print` 能看到回调执行两次），进度条动画会跳两下。**结论：`connect` 不会自动去重。** 修法是连接前 `if not sig.is_connected(cb)`。

**实验 B：用 `CONNECT_ONE_SHOT`**

改成 `player.died.connect(_on_player_died, CONNECT_ONE_SHOT)`。故意让玩家死两次（把 `take_damage` 里 `if health <= 0: return` 注释掉）。

现象：第二次死亡时 `_on_player_died` 不再执行。**结论：一次性事件（结算、成就、剧情触发）用这个，能防重复触发。**

**实验 C：用 `bind` 传额外参数**

给 `health_changed` 连一个 `_on_health_changed_debug.bind("HUD")`，回调签名变成 `(current: int, maximum: int, source: String)`。

现象：`source` 拿到 `"HUD"`。**结论：`bind` 的参数永远排在信号参数之后。**

**实验 D：把信号改成无参数，观察耦合怎么回来**

把 `signal health_changed` 改成无参，HUD 回调改成自己 `player.health` 去读。

现象：能跑，但 HUD 现在必须持有 player 引用并知道 `health` 这个字段名。**结论：信号参数设计得越完整，接收方越不需要认识发送方。** 这是「信号好不好用」的分水岭。

## 六、常见错误与排查

| 现象 | 原因 | 修法 |
|---|---|---|
| 信号发了，接收方没反应 | 忘了 `connect`，或连在了另一个实例上 | 打断点看 `sig.get_connections().size()` |
| 一次事件触发两次 | 重复 `connect` | 连接前 `is_connected` 判断 |
| `Attempt to call function 'connect' on a null instance` | `get_node` / `get_first_node_in_group` 返回 null | 加判空，检查节点路径与组名 |
| 报 `Invalid call. Nonexistent function 'xxx'` | 旧写法 `connect("sig", self, "func")` | 改成 `sig.connect(func)` |
| 回调里改场景树时报错 | 信号在物理帧里发出，立刻 `queue_free` 或 `add_child` 有风险 | 用 `CONNECT_DEFERRED`，或 `call_deferred` |
| 信号参数对不上，静默不触发 | 回调参数个数 / 类型不匹配 | 打开 Errors 面板，连接失败会有警告 |

**排查三步法**：① `sig.get_connections()` 看连了几个；② 在 `emit` 那一行打断点，确认真的走到；③ 在回调第一行 `print`，确认真的进来。

先自己答，答完再回去对照。答不出的，回去重读对应小节。

1. 一个信号最多可以连接几个接收者？
2. `connect` 的 `CONNECT_ONE_SHOT` 解决什么场景的问题？
3. 信号能带返回值吗？为什么？
4. 为什么要在 `_ready` 里手动 `emit` 一次初始状态？
5. 下面这段为什么会在运行时崩？
   ```gdscript
   var player = get_node("../Player")
   player.take_damage.connect(take_damage)
   ```
6. `bind` 的参数和信号自身的参数，谁在前？
7. 什么时候该用信号，什么时候该直接调用方法？（这题最重要，答案在下面）

**第 7 题参考思路**：

- **用信号**：发送方不知道也不应该知道接收方是谁；一对多；跨层级（子 → 父 → 全局）。
- **用直接调用**：接收方是确定的、唯一的，且调用方本来就持有引用；同步需要返回值。
- **反模式**：为了「解耦」把所有东西都做成全局事件，最后没人知道一个事件被谁处理、按什么顺序处理。**信号是用来解耦「不该互相认识」的节点，不是用来隐藏依赖。**
